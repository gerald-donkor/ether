# 022 - Moderation and abuse handling

## Scope, and why it is next

**Build step 10, moderation and abuse handling.** Add prompt screening before
image generation, output screening before any generated bytes are stored, a
signed-in report flow for an existing shared image, and a non-destructive
takedown state that removes a confirmed unsafe generation from every rendered
surface without deleting its row or Blob.

This is next because phase one and build steps 5 through 9 are present in the
repository and committed through `2e1441e`. The current generate action moves
from quota reservation directly to the image model, shared records have no
report action, and the schema has neither `reports` nor a takedown state. Step
10 is therefore the first unbuilt row in `AGENTS.md` §5.2. Step 11 depends on
the final generation lifecycle and must not start first.

The implementation must not create an admin panel or invent an admin role.
Report review in this step is automated and bounded: a report is recorded once,
the existing image is re-screened once, and only a confirmed unsafe result may
stamp the generation's takedown state. A safe result records that no action was
taken. An unavailable or malformed moderation result leaves the report pending
and leaves the image unchanged. One report must never become an unverified
automatic takedown.

## Implementation contract

### 1. Moderation policy and provider boundary

Keep Cloudflare Workers AI as the only model provider and plain `fetch` as the
only transport. Do not enable AI Gateway Guardrails, create a gateway, add an
SDK, install another provider, or add an environment variable.

`lib/ai/generate.ts` remains the one module that reads
`CLOUDFLARE_ACCOUNT_ID` and `CLOUDFLARE_API_TOKEN` and the only module that
calls a model. It may gain focused internal helpers and exported moderation
functions, but no second file may call a Cloudflare model. Environment reads
remain inside functions, never at module scope.

Before writing the model constants or request bodies:

1. re-fetch the live Llama Guard page, the current vision-capable model pages,
   pricing, limits, data-use and error documentation;
2. verify that `@cf/meta/llama-guard-3-8b` is still available and not
   deprecated, and select one current Cloudflare-hosted vision model whose
   direct REST image input and output are fully documented or safely measured;
3. check whether a license acceptance is required. Do not perform a provider
   state change without the user's approval. Prefer an equally suitable model
   with no unaccepted license gate;
4. make safe, non-sensitive live probes when the environment is available to
   measure the exact envelope, moderation text shape, usage fields and
   `cf-ai-neurons` headers. Never put a real user prompt or stored user image in
   a probe;
5. record the selected IDs, prices, response formats, measurement date and any
   unresolved provider discrepancy in `docs/backend.md`.

Prompt screening uses the dedicated safety model with deterministic settings
and the minimum bounded output needed for its documented safe or unsafe
decision. Output screening sends the generated bytes, without the user's
prompt, to the verified vision model with one fixed, server-owned policy that
returns only a closed safe or unsafe outcome and a closed violation category.
The report re-screen sends the stored image plus the reporter's validated
closed category, never a free-text allegation.

Treat every model response as hostile. A strict parser accepts only the exact
closed outcome and known category values. A missing result, schema deviation,
unknown category, non-2xx response, `success: false`, timeout or unreadable body
is `unavailable`, never implicitly safe. Keep moderation policy text, parser
types and user-facing messages centralized. Do not log prompts, images, base64,
Blob URLs, request bodies or complete provider responses.

### 2. Provider metering and ordering

Moderation consumes the same account-wide Workers AI allocation as generation,
so it must enter the existing atomic provider-capacity boundary before any
moderation or image call.

Re-fetch pricing and measure response headers before choosing reservation
units. Use the existing integer scale only if it can exactly and conservatively
represent every verified moderation cost. If it cannot, migrate to the smallest
exact integer scale and update existing image-model units and the daily ceiling
without changing their real neuron values. Never round a reservation down.

For a generation request, reserve one atomic event for the complete worst-case
provider work that request authorizes: one prompt screen, the requested image
calls, and one output screen per requested image. The existing rolling account
image cap still counts only the requested image count. An unsafe prompt may
conservatively leave its accepted reservation spent, matching the established
crash and failure policy.

For a first report by one reporter against one generation, reserve provider
capacity for exactly one output re-screen without consuming the reporter's
rolling image allowance. Extend the usage-event schema and database function
through a reviewed migration so provider-only events can be represented
without pretending an image was requested. Keep one transaction-level advisory
lock, one UTC-day provider sum and fail-closed outcomes. Do not add a second
service or in-memory limiter.

The required generation order is:

1. await Clerk auth and reject anonymous use;
2. validate prompt, model, size, count and publication through the existing
   shared schema;
3. resolve and atomically reserve the complete closed-list provider cost and
   requested image count;
4. screen the prompt;
5. on a safe prompt, run the existing sequential image loop;
6. screen each returned image before Blob storage;
7. store bytes and write a generation row only for an image with a confirmed
   safe result;
8. revalidate only the surfaces changed by rows actually written.

An unsafe prompt returns one actionable refusal and makes no image call. An
unsafe output increments the existing failed count, writes no Blob or
generation row, and allows later images in the already-reserved sequential
batch to continue. Moderation unavailability fails closed with plain retry
copy. Preserve the existing partial-success contract.

### 3. Schema and migration

Add the report and takedown lifecycle through Drizzle. Generate the next
migration, inspect it, and append only reviewed SQL needed to replace the quota
reservation function atomically. Do not use schema push or ad hoc DDL.

The generation takedown state contains:

- `takedown_at`, nullable timestamp with time zone;
- one closed takedown reason owned by the moderation policy, nullable while the
  row is live;
- a database check that timestamp and reason are either both null or both set.

Do not overload `deleted_at`. Removed is the owner's undo state; takedown is a
safety state the owner cannot clear through visibility, restore or any client
field. A takedown retains the row and Blob for the report record and later data
rights work, but no existing page or public query may render its image URL.

Add `reports` with:

- UUID primary key with database default;
- generation UUID, not null, with the deletion behavior explicitly justified
  against the existing permanent-delete flow;
- reporter Clerk user id, not null and server-derived;
- one closed report category, not null;
- one closed result state that distinguishes pending, no action and takedown;
- `created_at`, not null with `now()` default;
- nullable `resolved_at`, paired by a database check with terminal results;
- a unique constraint or index on `(generation_id, reporter_user_id)` so one
  signed-in account can create at most one report for one image.

Do not store a free-text report, email, prompt copy, model response, confidence,
raw category string, IP address, user agent or request body. Add only indexes
proved by the actual report lookup and mutation predicates. The unique
reporter-generation key is both replay protection and the bounded write limit
for this path.

Update `usage_events` so a provider-only moderation reservation is explicit
and valid while generation events retain their existing meaning. Do not erase
or reinterpret committed usage. The `/account` image-used reading must continue
to count generation image units only; its compute reading may include all
owner-attributed provider work if that is what the migrated data truthfully
represents, and the label must say so.

### 4. Data-layer boundaries and takedown coverage

Put every report, moderation-state and takedown query under `lib/db/`. Server
Actions contain no SQL. Add narrow typed functions for:

- claiming the first report for a signed-in reporter and shareable generation;
- completing that claimed report as no action or takedown;
- atomically stamping takedown with its closed reason only when a confirmed
  unsafe report is completed;
- reserving provider-only moderation capacity;
- reading the minimum stored image data needed for the report screen without
  exposing it to the browser.

The claim must reject a private, removed, already-taken-down, missing or
owner-reported image with the same non-enumerating result. A duplicate report
is idempotent and must not reserve quota or call a model again.

Audit every generation read and mutation, not only the public queries. A
taken-down row must be absent from the landing gallery, Community, shareable
permalink, `/generate` history, `/library`, downloads, visibility changes,
remove and restore. The owner must not be able to republish or restore around a
takedown. Permanent deletion remains available through the existing
owner-authorized flow so data rights are not weakened. Decide and document
whether inventory counts include retained takedown records, then make the UI
label match the query rather than silently changing its meaning.

When a confirmed report stamps takedown, immediately expire
`public-generations` and revalidate `/`, `/community`, `/g/[id]`, `/generate`
and `/library`. Keep the current fallback artboard slots and Community empty
state, so removal of public data changes content but not either page's layout
family or render mode.

### 5. Report route and Server Action

Add `/g/[id]/report` under the existing `(generation)` shell. Keep `/g/[id]`
public for shareable rows. The report page may render to an anonymous visitor,
but it must direct them to sign in and the action must independently require a
Clerk session. Do not make all `/g/**` routes protected in `proxy.ts`.

The report link appears only on the non-owner view of an unlisted or public
generation. The report page awaits and validates `params`, reads only a
shareable, live, non-taken-down projection, and does not render the image,
prompt, owner id or Blob URL. It identifies the subject only as `This shared
image` and presents a closed reason select, Submit report, and Back to image.

The browser sends exactly `generationId` and one closed `reason` through
`FormData`. A shared Zod schema in `lib/validation/` runs on the client as a
courtesy and in the action as enforcement. The action:

1. reads the Clerk session and rejects anonymous use;
2. validates both fields;
3. claims the report through the data layer, which confirms shareability,
   excludes the owner, and makes duplicate submission idempotent;
4. reserves one provider-only moderation call;
5. fetches the stored image server-side with a bounded size and validated image
   media type before sending it to Workers AI;
6. screens it against the fixed policy and validated report category;
7. completes the report as no action or atomically stamps takedown;
8. revalidates only when takedown changed rendered data;
9. returns a discriminated, constrained result to the client leaf.

If the report row is claimed but quota, Blob fetch or moderation fails, leave
it pending and return `Report received. It could not be checked right now.`
Do not claim that a human review will happen. A duplicate returns `This image
was already reported from this account.` A completed safe result returns
`Report received.` A confirmed takedown returns `Report received. The image is
no longer available.` None exposes why another report was resolved, another
reporter, a provider outcome or a confidence value.

Use `useActionState` and `useFormStatus` in the smallest client leaf. Disable
the submit while pending, keep the status node mounted, move focus to it when
the action resolves, and prevent repeat submission after any accepted or
duplicate result. Use no toast, modal, animation or client fetch.

At minimum, tests cover:

- exact safe and unsafe prompt-parser results;
- malformed, unknown and missing moderation responses fail closed;
- the vision moderation parser accepts only its closed schema;
- report validation rejects unknown ids, categories and extra policy values;
- duplicate report claims do not call the provider path twice;
- a safe report leaves the generation live;
- a confirmed unsafe report stamps one takedown and is idempotent;
- every public and owner listing excludes a taken-down row where the contract

- visibility and restore cannot clear or bypass takedown;
- concurrent provider reservations cannot cross the daily ceiling, while

Keep pure parser and validation tests environment-free. Put database and live
provider checks behind explicitly named integration commands loaded through
`dotenv -e .env.local --`; never make `npm test` require real secrets. Provider
probes use synthetic safe fixtures only and do not print request bodies or
image bytes.

## Trust boundary

The generation browser input remains `prompt`, `model`, `size`, `count` and
`publish`. The action derives the Clerk owner id, validates the closed request,
reserves the complete provider budget, screens the prompt, then screens each
output before storage. The browser supplies no moderation model, policy,
category, cost, confidence or decision.

The report browser input is only `generationId` and a closed `reason`. The
action derives the reporter from Clerk, validates both fields, re-reads a
shareable non-owner generation through the data layer, and uses an atomic claim
to prevent replay. A private, removed, taken-down, foreign, malformed or missing
target never yields information that confirms its row exists.

Only a strict, confirmed unsafe model result may set takedown. Unknown or
unavailable results remain pending and do not hide content. The owner cannot
submit, clear, restore around or overwrite a takedown through a client field.
Permanent owner deletion remains separately authorized.
