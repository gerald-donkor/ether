# 010 - The four navigation routes

Build step 2 is next because build step 1 is committed as `a367b09` and its
route groups, authenticated shell, and nav auth state are present, while
`Learn`, `Build`, `Product`, and `Community` still render as `href="#"` in both
desktop and mobile navigation. No matching route exists under
`app/(marketing)/`.

This prompt creates those four public, static marketing routes and gives every
nav item a real destination. It does not begin the seven footer routes from
build step 3, the database-backed gallery from build step 4, or any phase-two
product work.

## Design read

Read this as four product-information pages for working creatives, in Ether's
existing dark studio-console language. This is a preserve-mode extension of a
finished visual system, not a redesign.

Use these design dials while judging the new work:

- `DESIGN_VARIANCE: 7` - the four routes must be recognisably related but use
  four different layout families.
- `MOTION_INTENSITY: 2` - static composition plus existing hover and active
  feedback only. There is no approved reason for new automatic motion.
- `VISUAL_DENSITY: 4` - concise, technical pages with enough substance to make
  each route useful, but no marketing filler.

The aesthetic risk is structural rather than decorative: each route explains a
different part of the same product through a different reading pattern. Do not
spend that distinction on a new palette, typeface, gradient, radius, glow, or
motion effect.

## Route content and layout families

All four pages are Server Components by default, export route-specific static
metadata, and remain statically renderable. They do not read `headers()`,
`cookies()`, `auth()`, search parameters, the database, Blob, or the AI Gateway.

The copy register is plain, technical, and confident. Use active voice, no
exclamation marks, no hype, no fabricated testimonials, no invented statistics,
and no visible em-dash or en-dash characters. Claims must be limited to behavior
already present in the committed repository: a signed-in user can submit a text
prompt, receive one square image when the configured provider succeeds, and
find private recent generations again on `/generate`. The Gateway billing block
recorded in `docs/backend.md` is an operational deployment issue, not marketing
copy and not content for these pages.

### `/learn` - an annotated field guide

Purpose: teach the user how to make a prompt more deliberate without claiming
that one formula guarantees a result.

Use a stepped, single-reading-column manual rather than a hero followed by
cards. Start with a compact left-aligned page lead, then arrange four prompt
considerations as offset typographic bands: subject, setting, light, and finish.
Each band gets one short heading and one short practical explanation. Insert
one existing artboard photograph as a full-width visual reference between the
bands, with accurate alt text and no claim that it was generated by Ether.
Finish with one `Open generator` action to `/generate`.

This family must not become an image-plus-text split, a feature-card row, a
numbered process, or a second landing-page hero.

### `/build` - a prompt assembly bench

Purpose: show how a concise prompt can be assembled from concrete choices.

Use a horizontal composition at `lg` made from four semantic prompt clauses,
connected by alignment and whitespace rather than card boxes or decorative
lines. The clauses collapse to a strict vertical sequence below `md`. Use one
existing artboard photograph after the sequence as a visual reference, not as a
fake generated result. End with one `Build in Ether` action to `/generate`.

Do not render a fake input, fake model controls, fake terminal, or mocked product
screenshot. Do not reuse `PromptField` here: its inert marketing behavior would
make this route promise an interaction it does not provide.

### `/product` - a capability ledger

Purpose: state what the committed product does today.

Lead with one broad existing artboard image inside `--r-card`, then use at most
four capability entries in a sparse ledger. The entries cover prompt input,
one square result, private recent history, and account identity. Each entry has
a direct heading and one short factual sentence. Rows may use a single divider
between entries, but do not box every item or build a three-equal-card feature
grid. End with one `Use the generator` action to `/generate`.

Do not mention model choice, image count controls, aspect-ratio controls,
sharing, downloads, editing, teams, billing, moderation, or quotas as product
features. Those belong to later build steps or internal safeguards.

### `/community` - a privacy-first threshold page

Purpose: give the nav destination an honest public page before build steps 4
and 8 add real public work and sharing.

Use a one-screen editorial poster family: a short statement, one existing
artboard crowd photograph used as atmosphere, and a compact status block below
it. Do not overlay labels or copy on the image. State plainly that generations
are private to their owner today and that a public showcase is not open yet.
Offer one `Create privately` action to `/generate`.

Do not show the extracted gallery photographs or avatar files as member work,
real users, testimonials, or public generations. Do not query the database and
do not create a static showcase that build step 8 would later have to undo.

## Measurements and responsive procedure

Use only the measured system in `design-system.md`:

- marketing chrome and footer stay on `--container-wide` through the existing
  layout; route content uses the existing `Container` with `width="inner"`;
- the nav remains 72px high, transparent, single-line at `lg`, and full-screen
  on mobile;
- section spacing comes from the existing 4px scale, with 120px as the normal
  desktop section rhythm and responsive reductions selected from the same
  scale;
- H1, H2, body, label, and button roles use the exact type sizes, weights,
  tracking, and loose display leading in `design-system.md` §1.3;
- all surfaces use `--r-card`, `--r-panel`, or `--r-pill`. No new route may use
  the gallery-only square-corner exception;
- every paragraph stays within 65ch;
- every responsive image uses `next/image`, reserves its intrinsic aspect
  ratio, has accurate or deliberately empty alt text, and sets `sizes` from its
  actual layout. No image on these routes gets `priority`;
- mobile layouts collapse explicitly before 768px. Validate the compositions
  at the recorded `sm`, `md`, `lg`, and 1440px artboard widths rather than
  inventing another breakpoint.

Use existing assets only. Suitable choices are the extracted photographs in
`public/assets/ui/img/`; never add stock, generated site imagery, or a new file
under `public/`. Reuse does not change the source image's meaning: captions and
surrounding copy must not identify an artboard photograph as a real generation,
member submission, or product screenshot.

Change the module-scope `LINKS` constant in `components/sections/Nav.tsx` from
labels to typed `{ label, href }` records for `/learn`, `/build`, `/product`, and
`/community`. Render both desktop and mobile items with `next/link`.

Preserve the existing label order, chevrons, desktop spacing, mobile dialog,
focus transfer, Escape handling, signed-in and signed-out branches, and visual
output. When a mobile nav link is chosen, close the dialog so the persistent
marketing layout cannot leave the menu open after client navigation.

This prompt changes the four nav destinations only. Footer links and social
links remain `href="#"` for build step 3.

## Render impact

- `/learn`, `/build`, `/product`, and `/community` are new public static routes.
- `/` remains static and visually byte-stable. Its only intentional HTML change
  is the four nav `href` values and the implementation detail that they render
  through `next/link`.
- Every route under the marketing layout receives the same real nav targets.
- `/sign-in`, `/sign-up`, `/generate`, and `/account` keep their current render
  behavior and output. The app shell is not modified.
- No route enables Cache Components, dynamic rendering, ISR, or data fetching.

Verify the render modes from the production build route table. Do not infer
them from this prompt.

## Trust boundary

None. These routes add no form, mutation, route handler, server action, request
body, user-supplied parameter, or user-content read. Navigation crosses only a
public route path into the Next.js router. `/generate` remains independently
protected by the existing proxy, app layout, page, and action checks from build
step 1.

## Secrets and data

The pages store, log, or transmit no user data, prompt, email address, request
body, generation record, or image. Do not import from `lib/db/`, `lib/ai/`,
`lib/storage/`, or `lib/auth/`.

## Constraints

- One dark theme from start to finish.
- Violet identifies and lime acts. A lime element is always clickable; violet
  is never a button fill; text on lime is ink.
- No raw hex in a component file and no edit to the established token set.
- Zero em-dashes or en-dashes in visible copy, metadata descriptions, alt text,
  or accessible labels.
- No invented numbers. The new pages need no statistics.
- No repeated page family. None of the four routes may become another
  image-plus-text split, landing hero grid, feature pair, stat split, gallery
  strip, logo wall, footer, or app form column.
- No new motion. Existing link color transitions and button active feedback are
  sufficient, so `design-system.md` §3 gains no motion row.
- Every keyboard stop keeps the global 2px lime focus ring at 2px offset.
- Phosphor icons, if genuinely needed, use direct SSR imports. Prefer no new
  icon when typography and layout already communicate the idea.
- Keep static arrays and content records at module scope. Do not create inline
  components or client components for static page content.
- Preserve the one-per-page image priority rule by adding no priority image to
  these routes.
